# Release Notes v0.3.0

Released: 2026-11-25

## Highlights

A runbook can now be run more than once. A deploy, unlike a launch, is
run every time: mark it `recurring`, begin each run with `restart`, and
`state` says when each run began, whether it finished or failed, and
when the runbook last finished.

## Added

- **Recurring runbooks.** `Runbook.Recurring` marks a runbook that is run
  again from its first step. `Log.Restart` begins a new run; the log
  keeps when each run began in `runs`, and every event. A step's state
  comes from the current run's events, so after a restart every step is
  `ready` or `blocked` again, and the earlier runs stay as history. A
  runbook that is not recurring refuses a restart.
- **The runbook's state.** `StateOf` returns a `RunbookState`: the
  current run and every run before it, each with when it started, who
  began it and why, its last event, when it finished, its outcome
  (`not-started`, `in-progress`, `failed` or `finished`) and its steps by
  state, and when the runbook last finished.
- **`Log.NextRunStart`** gives the earliest time a new run can begin, just
  after the last event, and **`Log.Current`** the current run's events.
- **Commands.** `restart` begins a new run, with `--note` and `--by`;
  `state` prints the runbook's state as text or with `--format json`.

## Changed

- **Schemas.** The event log adds `runs` and the runbook adds
  `recurring`. A log without runs is one run, so existing logs and
  runbooks read as before.

## Upgrading

No code change is needed. A host that mounts the commands with `cli.New`
gets `restart` and `state` with them.
