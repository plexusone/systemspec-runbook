# Release Notes v0.4.0

Released: 2026-11-25

## Highlights

Set everything up once, then run a whole phase. `prepare` lists every
variable and input a run needs and which are missing; `run <phase>` checks
them all before its first step, runs the phase's steps in order, and when
one fails says where it stopped and how to fix it.

## Added

- **Phase runs.** `run <phase>`, such as `run 8`, runs the phase's steps in
  order with `Runner.RunPhase`, skipping those already done or verified. It
  stops at the first step that fails, is stopped, or waits for a step
  outside the phase, and running it again resumes there.
- **Failure reports.** A failed run shows where it stopped: the phase, the
  step, the action and the command; the command's error and the last 20
  lines of its output, which still stream to the terminal; the fixes whose
  patterns match; and the commands that resume the phase or retry the
  step. The run returns it as a `Failure`. A failure's one-line error and
  its `failed` event are as before.
- **Troubleshooting fixes.** `Troubleshoot` on a runbook and on a step
  lists fixes: `match`, a Go regular expression matched against a failed
  command's output and error, and `fix`, what to do in Markdown. A step's
  come before the runbook's. `Validate` checks each pattern compiles; both
  pages list them.
- **Inputs.** `Runbook.Inputs` declares what steps need besides variables:
  a value in the environment, such as an API token, marked `secret` when
  it must never be shown or written, or a precondition a command checks,
  such as a key loaded in the SSH agent (`ssh-add -l` printing its
  fingerprint), each with `howTo`. `Step.Needs` names a step's inputs. A
  phase run checks every input its remaining steps need before the first
  starts, and a step's run its own.
- **prepare.** `prepare <step|phase|all>` lists every variable and input a
  run needs, each `set`, `missing`, `derived` (its command gives it when
  first needed) or `later` (an earlier command produces it), and how to set
  up each one missing. It only reads: it checks environment variables and
  runs inputs' checks, never a variable's command, never shows a value, and
  fails while anything is missing. `Runner.Requirements` and
  `Runbook.Remaining` do the same from Go.
- **Env files.** `--env-file` on `run` and `prepare` loads `NAME=value`
  lines, with `export` and quotes allowed and `$NAME` expanded as a shell
  would, without replacing what the environment already sets, and names
  the variables it set. `prepare --write-env` writes such a file to fill
  in, with no values, a secret's line commented, and never over a file.
  `LoadEnvFile` and `EnvTemplate` do the same from Go.
- **Before You Start.** The Markdown and HTML pages open with every
  variable, how it is set and the steps that use it, then every input with
  how to set it up; each step links the inputs it needs.
- `Runbook.Phase` and `Runbook.PhaseOf` look a phase up.

## Changed

- **Schema.** The runbook's JSON Schema adds `inputs`, `troubleshoot`, and
  a step's `needs` and `troubleshoot`. A runbook without them reads as
  before.
- A failed `run` no longer prints the command's usage after its report.

## Upgrading

No code change is needed. A host that mounts the commands with `cli.New`
gets `prepare`, `run <phase>` and `--env-file` with them, and its pages
gain Before You Start when the runbook declares variables or inputs. A
host that places the HTML fragment in its own page with its own style
sheet adds `Style`'s `.fixes` rule, or uses `Style`.
